## 本轮范围

三件事：图片全量 WebP 化 → 消除渲染阻塞 → 砍掉未使用 CSS。依据全部来自你贴的报告数字 + 我对构建产物与源码的实测。

## 一、图片全部 WebP 化

### 1.1 静态图片（本地转好提交，**不在服务器构建期处理**）

| 文件 | 报告/实测现状 | 目标 |
|---|---|---|
| `banner2.png` | 1448×1086，**1,858.4 KiB** | WebP q85 ≈ 200–250 KB |
| `nahida_music.png` | 1254×1254，373.8 KiB，显示 ≤150px | 320px WebP ≈ 20 KB |
| `music_player.jpg` | 1279×1779，254.5 KiB，显示 64px | 160px WebP ≈ 8 KB |
| `Personal_img.jpg` | 875×962，46 KB，头像显示 94×94 | 188px WebP ≈ 8 KB |
| `about_avatar / skills / contact / blog.jpg` | 合计约 710 KB | 按 16:9 卡片展示尺寸（≤1100px 宽）转 WebP |

做法：用 server 里**已有的 sharp**（`server/node_modules/sharp`，不新增依赖）写一次性转换脚本，产物提交进仓库；源码保持现有 `import x from '...'` + `.src` 写法，零架构改动。服务器 1G 内存，绝不在构建期跑图片处理。转好的 `banner2` 与头像我会先贴给你目测确认再提交。刊头图被 CSS filter 压暗，WebP 的差异肉眼不可见。

### 1.2 三个必须保留原格式的例外

- **`og-image.jpg` 保持 JPEG**：微信/QQ/LINE 等社交抓取对 WebP 支持不一致，OG 图必须最兼容。它只在爬虫抓取时下载，不进首屏。
- **favicon 用 PNG 而不是 WebP**：浏览器对 WebP favicon 支持不完整。把 243 KB / 256×256 的 `nahida.ico` 换成 32×32 + 48×48 PNG 图标，另加 180×180 `apple-touch-icon`。
- **`/cursor/*.ani` 不是图片**，保持 `.ani`（见第三节）。

### 1.3 死资源清理（共 12.8 MB，零引用）

`about_hero.jpg`(9.28 MB / 4K)、`Nahida.png`(2.12 MB)、`background_0.png`(1.67 MB)、`banner.jpg`(120 KB)、`src/assets/ico/nahida.ico`(243 KB 重复副本)、`public/favicon.ico`(未引用，Layout 指向 nahida.ico)。它们不进 dist，但拖累部署与备份。

### 1.4 动态封面：本轮建议不动（说明理由）

报告里两张 `/uploads/**.webp` 封面共 533 KiB（365.0 + 168.4）。上传管线已经是 WebP q85，但**不限制尺寸**，所以原图直接被当卡片封面用。后端其实已经为每张图生成了 400px 的 `.thumb.webp`（`image.thumb_path`，`image.vo.js` 也暴露了 `thumb_url`），只是 `PostVO` 没往外给。我不在本轮动它，因为 400px 缩略图放在约 550px 宽的卡片上（retina 更明显）会明显偏软，正确做法是加一个 800px 卡片规格——那属于后端图片管线改动 + 存量回填，建议下一轮单独做。如果你愿意先用 400px 拇指换这 533 KB，告诉我，我把 VO 字段一起加上。

## 二、渲染阻塞（报告：223.3 KiB / 870 ms）

根因只有一个：`GlassPanel.css` 212.2 KiB / 370 ms。里面 97% 以上是 LXGW 的 582 条 `@font-face`（实测 565,525 B raw / 216,951 B gzip），真正用到的只有 regular + bold 那 194 条——**Mono 三档与 Light 一档在 `src` 里零引用**（已 grep 全站 `font-family` 与 `font-weight`：只有 `'LXGW WenKai'`，字重只有 400/700/500/600，没有任何 300）。

三步改法：

1. `src/main.css:4` 的 `@import "lxgw-wenkai-webfont/style.css"` 改成只引 `lxgw-wenkai-regular.css` + `lxgw-wenkai-bold.css` → 565 KB 降到 210 KB（582 → 194 条 `@font-face`）。
2. 把字体 CSS 从 `main.css` 拆出来，在 `Layout.astro` 里改成独立的**非阻塞**样式表（`rel="preload" as="style"` + `onload` 切 `rel="stylesheet"`，配 `<noscript>` 兜底）。字体本来就设了 `font-display: swap`，所以首屏会用系统中文先渲染、文楷随后换入；`main.css`（CSS 变量、主题、重置）继续阻塞，不会闪样式。
3. `astro.config.mjs` 加 `build.inlineStylesheets: 'always'`。字体 CSS 拆走后每页只剩约 11 KiB 页面 CSS，直接内联进 HTML → **渲染阻塞请求数归零**，报告里那 4 个「130 毫秒」的小文件也一起消失。

预期：223.3 KiB / 870 ms 这项清零，报告的「渲染阻塞请求 — 预计缩短 750 毫秒」应消失。唯一可感知代价是首屏一次字体替换（系统中文 → 文楷）；如果你不接受这个替换，退路是只做第 1 步（阻塞从 212 KiB 降到约 65 KiB，观感零变化）。

## 三、未使用 CSS（报告：549 KiB = 339.4 + 210.0）

### 3.1 字体那 210.0 KiB

由第二节第 1 步解决。需要诚实说明：因为字体 CSS 仍在审计窗口内加载，这项**不可能归零**——瘦身后大约降到 64 KiB 左右。要真正归零只能放弃自托管 CJK 字体（观感变化大），不建议。

### 3.2 光标那 339.4 KiB —— 报告里的最大单项

改法：`Layout.astro` 不再在加载时调 `initCursors()`，改为**首次指针移动/按下/按键才初始化**（`pointermove` / `pointerdown` / `keydown` 三个一次性监听），并在 `(hover: none)`（触屏）、`prefers-reduced-motion: reduce`、`navigator.connection.saveData` 下直接跳过。

效果：Lighthouse 的审计窗口里没有指针输入，这 347 KiB 的 `<style>` 根本不会生成，11 个请求（1.12 MB）也不会发出 → 未使用 CSS 归零、网络负载少 1.12 MB、报告里那两个 62ms / 58ms 的「无法归因」主线程长任务大概率一起消失。真实体验不变：鼠标一动动效光标立刻出现（`ensureInjected` 的幂等逻辑保留，ClientRouter 软导航后仍能补回）。

顺带：给 `/cursor/*.ani` 加长缓存头（目前完全没有 `Cache-Control`，回访还会重新校验）。

## 四、同批建议（成本极低，命中同一份报告的其他红项）

- **mp3 改为首次播放才加载**：网络负载第一项 3,656.6 KiB，占第一方 49%。`src/stores/music.ts` 去掉 store 初始化时的 `loadTrack(0)`、`audio.preload = 'none'`，首次点播放再 load（`togglePlay` 里已有加载分支）。两行改动省 3.6 MB。代价：未播放前时长显示 0:00。
- **highlight.js 移出全局包**：`src/pages/_app.ts` 引了 `@/utils/mdEditorSetup`，把 highlight.js（约 153 KB）+ md-editor 配置（约 25 KB）塞进了每个页面都加载的 `_app.js`（194 KB / gzip 68 KB），而它只有文章页需要。把 import 移到 `PostDetailView.vue`（`Layout.astro` 的服务端 import 保留，SSR 代码高亮不受影响）→ 非文章页每页少约 62 KB gzip，同时消除 hljs 在 `_app` 与 `PostDetailView` 的重复代码。这一项关联的报告面板我还没看到（「减少未使用的 JavaScript」），但 `_app.js` 是首页 JS 397 KB 里最大的一块。
- **首页合并重复请求**：现在有两次 `GET /tags`（左栏 TagBox 与 HomeView 内的移动端 TagBox 各一次），复用项目已有的模块级单例模式合并为一次。
- **`PersonalCard` 去掉 `client:load`**：该组件没有任何事件、生命周期或 pinia，去掉指令后 Astro 直接渲染成静态 HTML、零客户端 JS，少一个岛。

这四项你可以全要、只挑前两项、或者都不要——本轮严格只做前三节也完全成立。

## 五、施工与验证

- 顺序：先图片（纯资源替换，最易回滚）→ 字体瘦身 + 拆分 + 内联（阻塞归零）→ 光标延迟 → 可选四项。
- 每轮改完：`npm run build` + `npm run check`（home 以 astro check 0 error 为准）→ 提交 → 服务器 `git pull` → `cd frontend/home && npm install && npm run build` → `pm2 restart blog-web`。
- **不碰数据库结构、不改 API 契约、不新增依赖**，全部可单人回滚。
- 验证清单：文章页代码高亮（亮/暗双主题）、六个列表页 + 文章页渲染、文章过渡卡片、音乐播放器播放、光标动效（移动鼠标后出现）、≤768px 移动端、`prefers-reduced-motion` 下无动效。
- 回归预期：再跑 PSI 时「渲染阻塞请求」应消失、「减少未使用的 CSS」从 549 KiB 降到约 65 KiB；网络负载第一方从 7,466.5 KiB 降到约 1,000–1,500 KiB 量级（若采纳第四节两项则更低）。字体 woff2 子集的实际请求数无法在无浏览器环境下实测，这部分是区间估计而非承诺。
